Demystifying Software-Defined Networking (SDN)

July 16, 2023

What is SDN?

Almost every formal definition of SDN you see on the internet talks about the splitting of the control plane and data plane. That’s usually the first thing we hear when you ask a person, “What is SDN?” As someone new to the concept, I found myself wondering—what exactly does that mean, why was it necessary, and how were things done before? These are the main questions we’ll explore in this post. The diagram below illustrates how traditional networking tightly coupled various planes of operation, and how SDN reshapes that architecture to better manage networks. Traditionally, each device contained its own control, configuration, and data planes. This made network management complex, slow to respond, and difficult to scale. The roles of each plane are outlined below. This tight integration meant all three planes were bundled together, typically running proprietary software provided by each hardware vendor.

  • Configuration and Management Plane: Handles the setup, monitoring, and administration of network devices.
  • Control Plane: Determines how traffic should flow through the network by using routing and signaling protocols such as OSPF, BGP, and ISIS.
  • Data or Forwarding Plane: Executes the actual processing and transmission of data packets based on decisions made by the control plane. It handles actual packet forwarding using ASICs.

In contrast, SDN decouples the control plane from individual devices and centralizes it in an SDN controller. Running the control plane on every device leads to inconsistent policies, complex configuration, and slow convergence in large networks. SDN solves this by centralizing decision-making, making networks more programmable and easier to manage. Additionally, an SDN controller can be centralized or logically centralized but physically distributed for better fault tolerance, using east-west peering between other controllers. At its heart, SDN splits the control plane (the part that decides where traffic goes) from the data plane (the part that actually moves the traffic). Instead of configuring every router or switch by hand, SDN uses a centralized controller—like a network command center—that runs the show. We can program the controller using software (hence “software-defined”) through APIs like REST.

Where does SDN shine? Think about these scenarios:

  • Cloud providers like AWS or Azure, managing millions of virtual machines (VMs) for different customers.
  • Data centers, juggling massive traffic for low latency.
  • IoT networks, connecting thousands of devices with unique needs.
  • Telecoms, using SDN for 5G to deliver tailored connectivity.

Examples of few well known SDNs are VMware NSX, Cisco ACI, and Juniper Contrail.

How Traditional Virtualization Handles Networking

Alongside SDNs, virtualization tools like KVM or Hyper-V were the MVPs for creating virtual machines. These tools are fantastic at slicing up physical servers into virtual ones, handling compute and storage like champs. While they offer some networking capabilities too, for full network management at scale involves an additional layer of abstraction and complexity.

In traditional virtualization, networking connects VMs to each other and the outside world using:

  • Virtual Network Interfaces (vNICs): These are virtual versions of physical network cards assigned to each VM. They allow VMs to send and receive packets as if they were connected to a real physical network.
  • Virtual Switches (vSwitches) like Linux bridge or Open vSwitch: Software-based switches inside the hypervisor that connect vNICs from multiple VMs and bridge them to the physical network.
  • Networking Modes: NAT (where VMs share the host’s IP), bridged (VMs appear as independent devices on the LAN), or host-only (VMs only communicate with each other and the host).
  • Physical NICs: The host’s actual hardware network interface cards that link the virtualized environment to the external network infrastructure.

This setup works for small environments, but it’s like building a model airplane by-hand, which is doable, but not ideal for a fleet.

Why Traditional Network Virtualization Falls Short

Traditional virtualization networking gets the job done for small setups, but it’s slow and doesn’t scale. Here’s why it’s inefficient, especially for big networks:

  • Manual Configuration: Tedious and error-prone for large environments.
  • No Central Control: Each host is a silo, with no global oversight.
  • Scalability Limits: VLANs are limited to 4096 IDs.
  • No Programmability: Hard to automate or apply dynamic policies.
  • Multi-Tenancy Woes: Limited tenant isolation with VLANs.

SDN Excels at Multi-Tenant Overlay Networks

One of the killer features of SDN is how elegantly it handles multi-tenant network virtualization through the use of overlay networks. In large-scale environments like cloud data centers (think AWS VPCs or OpenStack Neutron), each tenant typically gets its own isolated network.

To implement this on top of shared infrastructure, SDN systems use overlay or tunneling protocols such as:

  • VXLAN (Virtual Extensible LAN)
  • GENEVE (Generic Network Virtualization Encapsulation)
  • GRE (Generic Routing Encapsulation)
  • STT (Stateless Transport Tunneling)
  • NVGRE (Network Virtualization using Generic Routing Encapsulation)
  • MPLSoGRE (Multiprotocol Label Switching over GRE)
  • MPLSoUDP (Multiprotocol Label Switching over UDP)

These protocols encapsulate tenant traffic inside a tunneling header, allowing thousands or even millions of isolated logical networks to coexist on a single physical network fabric.

While hypervisors like KVM and Hyper-V do support these protocols, they lack the centralized intelligence of SDN. Without a controller, you’re back to scripting and static configs—which quickly becomes unmanageable at scale.

What Problems Does SDN Solve

Lack of automationCLI or scripting per hostDeclarative APIs, automated provisioning

With SDN:

  • Spin up isolated tenant networks instantly
  • Apply policies uniformly across clusters and regions
  • Support dynamic service chaining and traffic steering
  • Easily scale to millions of logical networks without hitting VLAN limits

So while virtualization gave us agile compute, SDN gives us agile, programmable, and isolated networks—a perfect pairing for the modern cloud-native world.

TL;DR: Compute Virtualization Needs Network Virtualization. That’s how modern platforms like OpenStack, AWS, Azure, and GCP manage to provision entire networks for tenants in seconds, with full isolation, security, and scale.

SDN with Network Functions Virtualization (NFV)

Modern SDN platforms have evolved beyond simple traffic steering. Today, they are often integrated with Network Functions Virtualization (NFV)—the concept of running network services as virtualized software components on commodity hardware. This includes:

  • Load Balancer as a Service (LBaaS): Dynamically spin up virtual load balancers for applications.
  • Firewall as a Service (FWaaS): Centralized policy enforcement across virtual networks.
  • VPN as a Service: Offer secure, tenant-specific tunnels over shared infrastructure.
  • WAN Optimization and DPI (Deep Packet Inspection): Deploy network appliances as software functions, easily managed via the SDN controller.

By combining SDN and NFV, operators can automate not just the flow of traffic but also the provisioning of complex services—turning what used to be expensive, specialized appliances into agile, on-demand software.

SDN and SD-WAN

While SDN focuses on abstracting and centralizing control across any network type, SD-WAN is a specialized use case that brings those benefits to geographically distributed networks. It doesn't replace SDN but rather extends its core ideas to simplify WAN operations and improve user experience at the edge.

Final Thoughts

To give a better analogy, OpenStack uses Neutron to manage networking, but for more advanced capabilities—such as fine-grained traffic control, virtual routing, and automation—it often integrates with SDN controllers via plugins. Examples include Ryu (os-ken), OpenDaylight, Contrail, which extend Neutron’s functionality by offering programmable, scalable network control. Similarly, Kubernetes includes a basic networking component called kubenet, which provides minimal connectivity for pods. However, in production environments, it's common to use third-party networking solutions that integrate with Kubernetes through the CNI (Container Network Interface) plugin system. These CNI-compatible solutions provide more robust networking features such as network policy enforcement, IP address management, and multi-cluster connectivity. Popular CNI implementations include Calico, Cilium, Flannel, Weave Net, CN2 etc. Both ecosystems—OpenStack and Kubernetes—leverage network virtualization and software-defined networking to offer flexible, programmable, and scalable infrastructure. This enables dynamic service provisioning, efficient resource utilization, and faster network operations without relying on proprietary hardware appliances.
